# 臂 B 作答（完全无记忆 · 对照臂）

作答依据：每案给定的「工具 + 一行报错」＋通用工程经验。未使用任何记忆/检索来源。

## case-01

**1. 可避免吗 / 动手前做什么**
多数可避免，少数不可。可避免的路子：在调用 `edit` 前，按规定先读过目标文件，再从刚读到的**当前内容**里截取锚点，并选有唯一性的一段（含足够上下文）；确认锚点里的缩进、行尾、空行与文件实际一致；带换行的锚点要么整段复制，要么干脆避开——若锚点落在可疑的行尾/缩进边界上就不该用它。
**2. 不可避免的部分**
三类情形结构性不可避：① 锚点只存在于意图而未存在于文件（读后写前文件被别的进程/自己前序动作改过，形成读—改竞态）；② 隐形字符差异——CRLF/LF、BOM、不换行空格、全角空格、零宽字符、被工具改写过的引号，肉眼比对不可靠；③ 逐字替换本身要求精确匹配，`edit` 不做模糊或正则匹配。
**3. 改做法**
失败后不做同参重试；立刻重读文件，用工具搜索结果定位目标片段的**当前**原文，用新读到的原文重建 `old_string`；把该锚点的最短唯一子串锚死（只取一行里足够区分的那一段），缩小易漂移面；编辑后做一次复核读或搜索确认改动落位；同一回合内把「读 → 编辑」的间隔压到最短，减少读—改竞态窗口。

## case-02

**1. 可避免吗 / 动手前做什么**
可避免。`cordis_inspect_query` 只接受 Inspect Provider 清单里实际声明的方法名，调用前应先列清单取方法名，再按该方法自己声明的输入 schema 传参；方法名本身（含英文用词）也要以清单为准，不从常规语言习惯或相邻概念外推；调过被拒后不要换输入重试，先把可调方法集与签名取到手。
**2. 不可避免的部分**
如果清单缓存过期或与运行中的实例版本不一致，则按它取到的方法名也可能不存在——这属于**清单与运行时漂移**，靠报错前的检查覆盖不到；此时同签名重试不是稳定修复，需要重新取一遍清单。
**3. 改做法**
把「先枚举可用的 provider/方法，再精确调用」固化为这类 inspect 类工具的固定前置步骤；同名概念不跨工具迁移（某个概念暴露过的方法名，不代表另一个特性用同样命名）；把「未知方法」当契约问题而非参数问题处理，遇到就回头核对契约，绝不盲试近名方法。

## case-03

**1. 可避免吗 / 动手前做什么**
部分可避免，主因在环境不在命令。动手前先看目标路径里有没有常被独占的条目（正在写入的日志、临时文件、被进程持有的数据文件、自己刚起过的后台任务留下的句柄），避开那些路径；若命中，就别对目录做整树扫描，改用文件白名单/排除，或先等写入方安静下来。
**2. 不可避免的部分**
os error 32/33 是 Windows 的共享冲突与部分锁定，属于操作系统的文件锁语义，与搜索工具的写法无关：任何进程（包括本会话自己刚启动的后台进程）持有独占句柄时，外部读取会被系统直接拒绝；且它对**目录遍历中的部分条目**即致命（报错即 exit 2），无法保证只跳过锁定项继续。锁定往往发生在恰好要搜的文件上，时点不可完全预测。
**3. 改做法**
识别根因是「锁」而不是「没找到」——别把 exit 2 误读为零命中；先查谁在拿句柄（自己起的后台/驻留进程优先怀疑）；能停就停、能用释放句柄的方式重开再搜；不能停就换策略：先复制/快照到工作区再搜，或把扫描面从整树收窄到非锁定文件；把「搜日志活文件」这类操作默认改为对快照副本做。

## case-04

**1. 可避免吗 / 动手前做什么**
可避免。发出调用前，与实际可用的工具清单核对工具名。
**2. 不可避免的部分**
基本没有可辩护的不可避免成分：这是纯名称层面的硬失败，与目标、路径、参数、权限全都无关；同一次调用无论重试多少次结果都一样。
**3. 改做法**
不凭旧习惯构造工具名；遇到「未知工具」只认报错回显，照着清单改回真实工具名；需要并行调用时，改为按当前可用能力逐个发出独立调用，不假设存在批量编排入口；对整类失败建一条纪律：工具名类错误一律当场核对清单，不重试原调用。

## case-05

**1. 可避免吗 / 动手前做什么**
可避免。使用 offset/limit 前先确定文件真实行数：先做一次不带分页参数的完整读取拿到总行数与内容，再翻页；只有确实超出单次返回上限时才改用分页。关键纪律：**永不硬编码 offset 大于已确认长度的值**——只能从已读到的行号向后推进，或从文件尾回读。
**2. 不可避免的部分**
若文件在分页期间被改短（行数收缩），原本合法的 offset 也会越界——这属于读—改竞态，无法靠调用前的检查消灭，只能发现后重取。另：不完全确定的截断实现可能让「先读一次」拿到的是被裁剪的内容，行数以得到的信息为准并保留怀疑。
**3. 改做法**
先整读、后分页，offset 只从已知行号外推；offset 越界后不重试旧值，直接重读或改从尾部读；把该文件当作「长度未知」处理，引用行号时不做猜测；大文件采用「搜索定位行号 → 围绕该行精读」的方式。

## case-06

**1. 可避免吗 / 动手前做什么**
可避免。该参数有硬性区间（1–300 秒），动手前读一次 schema 或调一次默认值，把入参落在合法区间内；对已知有上限的「时间/长度/并发」类参数统一先做范围预校验再调用；若预估任务耗时可观，从一开始就按「能塞进上限的粒度」设计命令。
**2. 不可避免的部分**
任务本身可能需要比上限更长的时间，那不是参数错误而是能力边界：单一调用确实无法承载超过 300 秒的工作，只能换执行形态，重试与调参都改变不了这一点（上限是该工具契约的一部分，不是可议的软限制）。
**3. 改做法**
超限时一次性修正到合法区间，不盲目重试；长耗时改用后台执行 + 轮询取结果，或把工作拆成多个各在额度内的块；把「先自测一下耗时再定 timeout」写进习惯；看见区间提示就当场映射到区间内，不留下一次同类错误。

## case-07

**1. 可避免吗 / 动手前做什么**
对「错误命令本身」不可避，对「造成它的环境变更」可避免。Windows Job runner 是宿主用来圈定进程范围的机制，它必须能在宿主认可的环境里启动子进程、并证明自己管理的进程集为空（正常退出），否则整条 pwsh 通路失败——退出码是无符号的 -1/0xFFFFFFFF。触发点通常是**宿主进程的全局环境被污染**（环境变量/运行模式被整体改动）。
动手前的正确动作：把「修改宿主环境变量」识别为进程级、影响面全局、且不可在进程内回滚的动作；改前先记录原始值、写清回滚命令，并把改动收窄到具体应用的启动路径，而不是从宿主环境全局清理；改后立刻用一条最便宜的调用做探针验证。若无法现场验证，就拒绝执行该变更、交人工决策。
**2. 不可避免的部分**
一旦污染已经发生，就这一调用而言不可避：runner 起不来属于请求发出前就已存在的机器状态；且它在宿主通道层失效，同会话内没有恢复手段（进程内无法自愈），任一命令都会以同一方式失败。重试无意义。
**3. 改做法**
不重试同类命令，立即改走文件/WSL 通道继续推进手头的活，并把「需要重启运行时才能恢复」作为结论上报；把环境基线检查放进流程起点；把「宿主级不变量（环境变量、启动输入配置、运行时目录）只读」当硬纪律；任何环境类变更必须一次性带齐：现场备份 → 最小范围修改 → 探针验证 → 回滚路径，并在收尾记录「做了什么 + 一句回滚命令」，供下次同类报错直接对号。

## case-09

**1. 可避免吗 / 动手前做什么**
可避免。目标是单文件（而非目录）时，动手前先确认该路径存在且是普通文件：核对大小写、空格、反斜杠/正斜杠、是否短名或符号链、是否引号把路径吞进模式里；报错回显里的 `<path>` 就是实际被打开的对象，先拿它逐字符核对；路径里混有 `*`/`?` 或来自另一次输出拼接时尤其要复核。
**2. 不可避免的部分**
若路径在调用前已被移动/改名/删除（多是自己上一回合的动作或异步任务所致），则时点上的「不存在」不可预知；这类错误与权限问题还容易混淆——先分清「找不到」与「拒绝访问」是两套根因，别拿一个去修另一个。
**3. 改做法**
对单文件搜索前先做存在性与类型检查（普通文件 vs 目录），再发搜索；搜索对象是按通配符展开得到的话，先枚举实际文件列表看一眼再搜；路径不存在时不做同参重试，改为从父目录向上定位真实名，或回到产出该路径的那一步追改；把「先枚举、后搜索」变成对生成式路径的默认动作。

## case-10

**1. 可避免吗 / 动手前做什么**
可避免，且与 case-05 同族。调用分页读取前先拿到该文件的行数（一次整读，或围绕已读内容推进），再把 offset 落在 `1..N` 内并给 limit 一个合理值；分页游标只从**已成功读到的最后一行**往后推，不从注释、计划、上一次会话里的数字续推。
**2. 不可避免的部分**
同样只有一条不可避路径：文件在分页期间被改短，使先前合法的 offset 失效；此时唯一可信的是重取一次真实长度。
**3. 改做法**
先定长、再翻页，绝不让 offset 悬空；把「offset 越界」当作长度认知错误的信号而非可重试错误，立刻重读并修正对文件长度的认知；对会变化的文件，翻页后做一次收尾校验（末尾行号是否仍与预期一致）；同一纪律覆盖所有带 offset/limit/range 的工具，不逐案记忆。
