## case-01
1. 可以避免。动手前先读一遍目标文件，核对要替换的真实内容；old_string 应从刚读到的文本中直接复制，并确认空白、大小写、换行与缩进完全一致，而不是凭记忆或旧内容拼串。
2. 不适用。只要遵循“先读后改、用最小唯一锚点”，这次失败就能规避；失败后应重读定位差异再改，而不是盲目猜测重试。
3. 改法：调用 edit 前总是先 read 当前内容；old_string 直接取自刚读到的文本；找不到时先重读并定位差异再修正锚点；大段替换优先按行号/区间操作，少依赖大段原文精确匹配。

## case-02
1. 可以避免。调用前先枚举或查询该 provider 实际暴露的方法（能力列表、schema、帮助信息），确认 describeService 存在且拼写正确，而不是凭猜测或记忆直接调用。
2. 不适用。方法名是否存在是可以预检的，属于调用方未先确认接口能力，不属不可控因素。
3. 改法：对陌生或插件式接口先做能力探测（列出可用方法）再调用；只使用文档或探测结果中存在的规范方法名；名字不确定时先查询确认，不直接调。

## case-03
1. 部分可以。动手前检查目标路径是否正被其它进程打开或写入（日志、临时文件、正在保存的文档），换到稳定副本或等写入结束后再 grep；对易变的被锁文件预先排除或加等待重试。
2. 若锁由外部进程长期持有且无法控制其释放时机，则单次 grep 撞上锁定不可避免，只能靠等待或重试绕开。
3. 改法：默认扫描稳定、已提交的文件，避开活跃的临时目录与日志；把 os error 32/33 当作可重试错误，加短暂等待与重试；必要时先复制目标再搜索。

## case-04
1. 可以避免。调用前确认当前环境与接口 schema 中确实存在该工具名及其命名空间，不要假设某个别名在其他环境存在就直接使用。
2. 不适用。工具不存在是可预检的，属于命名或环境未确认，不属不可控。
3. 改法：先查看可用工具清单再选名，使用规范全名；并行能力不可用就回退为顺序多次调用，不硬套不存在的工具名。

## case-05
1. 可以避免。带 offset 读取之前先取得文件实际行数（如 wc -l 或整体读入），确认 offset 不超过行数，并对 offset + limit 做边界检查。
2. 不适用。行数是可以预先获得的，offset 越界属于未校验前置条件。
3. 改法：先测量长度再定位，offset 由实际行数推导并夹紧到合法范围；小文件直接整读；越界时回退为整读或从合法 offset 开始。

## case-06
1. 可以避免。传 timeout 前核对参数允许范围（1–300 秒），确认落在范围内再调用；报错本身已经给出合法区间。
2. 不适用。范围是已知且明确的前置校验，传入越界值属于可预防的错误。
3. 改法：调用前对数值参数做范围校验，越界先夹紧或向用户确认，不传未经验证的任意值。

## case-07
1. 基本无法在调用层避免。报错指向 Windows Job runner 在证明受管进程范围清空前就以 -1（4294967295）退出，更像宿主或运行器级的环境故障，不是单次命令参数可以直接预防的。
2. 不可避免的原因：根因在进程/Job 基础设施或环境状态，仅凭题面信息不足以定位，调用方无法提前知道何时触发。
3. 改法：把这类运行器级失败当环境异常处理：记录并重试一次，仍失败则上报环境而非反复改命令；不为绕过而改动无关代码；排查时区分“命令本身失败”与“运行器/Job 管理失败”。

## case-09
1. 可以避免。grep 前确认路径真实存在、拼写正确（Windows 下还要注意大小写与编码），不要复用已失效或被移动的旧路径；报错即“系统找不到指定的文件”。
2. 不适用。路径存在性可以预检，属于前置条件未核实。
3. 改法：先验证路径存在再搜索，优先用绝对路径或刚确认过的路径；对可能被删除或重命名的目标先检查再执行，失败后按“文件不存在”分支处理。

## case-10
1. 可以避免。与 case-05 同类：读取之前先取得真实行数（此处 128 行），offset 176 明显越界，应先校验再读。
2. 不适用。行数可以预先获得，越界属于未校验前置条件。
3. 改法：读前先测文件长度，offset 按实际行数夹紧；不硬编码来自旧快照或旧结论的行号；边界情况先读末尾或整读。
