## case-01
1. 可以避免。动手前先 `read` 目标区间或用 `grep` 定位行号，逐字核对原文，再据此写 `old_string`；注意缩进/空白/换行、全角半角、BOM/编码差异，且不要凭记忆或摘要拼 `old_string`——该行若已被更早的编辑改过，必须重新读取最终内容。
2. 绝大多数情况下都可避免；只有文件被另一进程在"读取原文"与"执行 edit"之间并发改写时，才存在动手前无法预知的外部竞争。正常的单机编辑流程不属于"不可避免"。
3. 改成"改前先读、逐字确认、一次一处、改后立即 `read`/`grep` 复核"；批量/并行 edit 逐个核对最终内容，不把"已更新 N 个文件"的计数当证据；大范围替换先 `grep` 列出全部命中点再逐点改。自检：「这次 edit 的 `old_string`，是不是我刚读到的原文？」读不到就不改。
→ 参考条目 canon-trap-edit-context-mismatch

## case-02
1. 可以避免。调用前先用宿主检视面（`cordis_inspect_list` / `cordis_inspect_query`）列出 provider 及其方法清单，照抄真实方法名；检视面查不到就查官方文档/源码导出，不凭印象硬编方法名。
2. 罕见地不可完全避免：当检视面、文档、源码都查不到该方法清单时，属于信息缺口；即便如此也不应凭印象硬编，而应先承认不确定。因此本例正常属可避免。
3. 改成"先列举再调用"；猜错一次后换路径（去列清单），而不是换拼写继续猜。自检：「这个方法名是我列出来的，还是我想出来的？」
→ 参考条目 canon-trap-provider-method-list

## case-03
1. 可以部分避免。动手前把搜索范围收敛到明确的文件或浅目录，确认目标文件当前未被其它进程占用（编辑器/索引器/数据库等）；对可能被锁的文件先关闭占用方或改用副本，避免对同一被占用文件反复搜索。
2. 部分不可避免：文件正被其它进程以排他锁占用时，grep 读到的是那一时点的外部状态，锁可能在动手前刚产生，无法在调用前完全预知；这类 os error 32/33 属于环境竞争，不是靠"换范围"就能绝对躲开。
3. 改成：grep 前先确认路径可用、范围收窄、排除 `node_modules`/`.git`/`data` 等；遇到占用/锁定类错误换副本或降范围，不要对同一被占用路径反复重试。自检：「这个路径适合 grep 吗？」
→ 参考条目 canon-trap-grep-exit2-path（条目主诉"路径不可访问/权限不足/目录不存在"，与本例"文件被占用/锁定 os error 32/33"部分吻合：权限/占用类失败适用其"换副本或降范围、不要反复重试同一路径"一条；先 glob 列文件、排除目录等为该条目给出的通用预防。）

## case-04
1. 可以避免。只从本会话真实可见的工具面里挑名字（工具清单/补全/上一轮真实调用），不照搬别家 harness 或通用记忆里的工具名；拿不准就先跑一次单工具验证名字是否真实存在。
2. 基本都可避免；仅当会话内完全没有可自省的工具清单、且从未调用过该工具时，才可能无从得知，但工具面一般可见，多数情况不属于"不可避免"。
3. 改成：多工具并行时只用宿主实际提供的那一个并行工具并先小规模试；不确定名字就先用单工具探路。自检：「这个名字我在本会话见过吗？」
→ 参考条目 canon-trap-unknown-tool-name

## case-05
1. 可以避免。动手前先 `grep` 定位目标行拿到真实行号，或先 `read` 头部确认文件总行数，不要沿用上一轮或凭印象的行号（本例文件只有 22 行却给了 offset 30）。
2. 基本都可避免；只有文件在"拿到行号"与"执行 read"之间被外部进程改短时，才可能踩边，属外部竞争。正常流程先定位即可避免。
3. 改成：`offset` 只用刚拿到的行号；报"越界"后不继续猜，改用 `grep` 锚点重新定位。自检：「我这个 offset 是刚拿到的行号吗？」
→ 参考条目 canon-trap-read-offset-range

## case-06
1. 可以避免。调用前先确认 `dsh_wsl` 的 `timeout` 参数合法取值域（1–300 秒），把值约束在范围内再调用，不给 0、负数或超过 300 的值。
2. 基本都可避免；仅当工具的取值范围没有任何可用说明、且只能靠失败后的报错才知道时，第一次调用才可能无法预知。多数工具在 schema/说明里已写明范围，故本例属可避免。
3. 改成：对带数值约束的参数，调用前先核对 min/max 与默认值再传；收到参数类报错后立即修正取值，而不是重复原值。自检：「这个参数值落在工具的合法范围内吗？」
→ 参考条目 无对应条目（资料库未收录 case-06 `dsh_wsl` 的 timeout 条目），本问按通用工程经验作答。

## case-07
1. 可以部分避免。exit code 4294967295 即无符号 32 位的 -1，指向 runner 进程异常退出/被终止、子进程树未按预期清空；动手前先检查命令是否会在 Windows Job/子进程环境里派生后台常驻进程、是否依赖继承来的畸形环境变量，先用最小探针命令验证通道可用再上正式命令。
2. 部分不可避免：这类"runner 在证明托管范围为空之前就退出"多为环境层故障（Job 对象、环境变量、进程树被连带杀死），根因往往在宿主环境，单次命令在调用前无法完全预知。
3. 改成：对子进程类工具先跑最小探针验证；失败后不反复重试同一命令，改查环境状态（进程树/环境变量/Job），必要时重启宿主再试。自检：「这个命令会 fork 后台进程、或依赖被污染的环境变量吗？」
→ 参考条目 无对应条目（资料库未收录 case-07 `pwsh` subprocess-local 条目），本问按通用工程经验作答。

## case-09
1. 可以避免。动手前先用 `glob`/列文件确认目标路径真实存在，用明确的文件或浅目录为范围，不 grep 一个已不存在或拼错的路径。
2. 基本都可避免；仅当路径在"确认存在"与"grep 执行"之间被外部进程删除/重命名时，才属外部竞争。正常场景先核对路径即可避免 os error 2。
3. 改成：grep 前先 `glob`/列文件确认路径存在；路径含空格/中文时加引号；报"系统找不到指定的文件"先核对拼写与大小写，而不是对同一路径重试。自检：「这个路径适合 grep 吗？」
→ 参考条目 canon-trap-grep-exit2-path
