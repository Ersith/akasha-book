# 独立评分解（第三方撰写 · 未接触任何内部资料）

以下每条均为“可在答案中逐项核对”的动作或论断，只依据各案例给定的工具名、一行报错与通用工程经验。

## case-01
- 必中：动手前先读目标文件，逐字核对 `old_string` 与文件原文完全一致（含空格、缩进、换行、标点）。
- 必中：报错即代表所给片段与文件当前内容不一致（写错、凭记忆，或文件已被改动）；应先读后改、不凭记忆重打。
- 必中：改进做法＝编辑前先取得原文，`old_string` 直接复制原文片段而非手敲；不一致时先查清差异，不盲试重试。
- 加分：选取文件中只出现一次的唯一锚点作定位串，并检查 CRLF/LF、编码及特殊字符转义差异。
- 加分：若该片段确实已不存在，说明目标状态可能已达成或文件已变，应重新读取判断，而非强行编辑。
- 扣分：说“edit 工具坏了/需要升级”——错误归因。
- 扣分：宣称“此类失败不可避免、无法预防”。

## case-02
- 必中：调用前先查询该 provider 实际支持的方法清单（帮助、自描述或能力探测），确认 `describeService` 确实存在且拼写正确。
- 必中：报错含义是“该 provider 没有此方法”，应先按真实可用方法名调用，或换成正确的 provider，而不是假定方法存在。
- 必中：改进做法＝调用前做能力/方法探测，用探测到的真实方法名，不凭记忆猜 API。
- 加分：区分“provider 存在但无此方法”与“provider 不存在”，据此决定换方法还是换 provider；考虑版本差异导致方法改名/移除。
- 扣分：说“服务没启动/服务挂了”——报错说的是没有该方法，不是 provider 缺失。

## case-03
- 必中：认清 os error 32/33＝文件被其它进程占用/锁定（不是“无匹配”，也不是语法错误）。
- 必中：动手前收窄搜索范围、排除已知会被独占锁定的路径（日志、数据库、运行目录），或先确认目标文件未被占用。
- 必中：改进做法＝把“部分文件读不到”作为可接受的降级处理：改用能跳过不可读文件的搜索方式，并单独核查报错列出的路径。
- 加分：对锁定文件先复制一份副本再搜，或定位并关闭占用进程。
- 加分：区分 os error 32（进程占用）与 os error 33（文件一部分被锁定）。
- 扣分：说“grep/ripgrep 工具坏了或不支持 Windows”——错误归因。
- 扣分：不改路径、不处理锁定就盲目重试。

## case-04
- 必中：承认调用了不存在/不可用的工具名，属于凭记忆或臆造工具名。
- 必中：动手前先查看当前环境实际可用的工具清单（工具描述/schema），确认工具名与参数。
- 必中：改进做法＝不臆造工具；并行只是调用组织方式，若不存在该封装工具就拆成多个真实存在的普通调用。
- 加分：对不确定的工具名，先在可用列表中验证再调用；失败后立即改用真实工具，而非重试同一假名。
- 扣分：说“需要安装/升级 multi_tool_use 插件”——方向错误。

## case-05
- 必中：动手前先确认文件实际行数（读一次不带 offset 或统计行数），再决定 offset 是否合法。
- 必中：报错已给出实际行数（22 行），应把 offset 调整到 ≤ 行数的范围，而不是继续用 30。
- 必中：改进做法＝对偏移读取先探测文件长度再设 offset，或用“读到文件末尾”语义代替固定大 offset。
- 加分：直接利用报错中的“22 lines”这一事实作为修正依据。
- 扣分：说“文件被截断/损坏”——报错明确说明文件只有 22 行。
- 扣分：不核对实际行数就换更大的 offset 重试。

## case-06
- 必中：动手前先看工具对 `timeout` 的约束（合法区间 1–300 秒），把值设进区间。
- 必中：报错已给出合法范围，应直接把 timeout 改成区间内取值（如默认值或 60/120）。
- 必中：改进做法＝调用前对每个参数做类型与边界自校验，不确定时用工具默认值；不传 0、负数或超大值。
- 加分：把参数范围检查前移到构造调用时。
- 扣分：说“WSL 不可用/命令超时”——报错是参数非法，不是执行超时。
- 扣分：说“必须把 timeout 改到 300 以上”——与报错方向相反。

## case-07
- 必中：正确解读退出码 4294967295＝0xFFFFFFFF（-1 的无符号表示），说明是 Windows Job runner 进程异常退出，而非 pwsh 命令自身的业务返回。
- 必中：认清报错来自 subprocess 运行器/进程树管理层（“before proving its managed range empty”），不是 PowerShell 脚本语法或命令失败。
- 必中：处置＝先重试判断是否偶发；若复现，检查运行环境（进程树是否被外部干扰、环境变量、并发子进程）并最小化隔离复现。
- 加分：先用最小化命令验证 pwsh 本身可用，区分“命令问题”与“runner/环境问题”。
- 扣分：说“PowerShell 命令写错了/脚本报错”——错误归因（报错不在脚本层）。

## case-09
- 必中：认清 os error 2＝系统找不到指定文件/路径，即传入的搜索路径不存在（写错、已被移动或删除）。
- 必中：动手前先核对路径确实存在（如 Test-Path/ls），确认拼写与位置正确。
- 必中：改进做法＝对将要搜索的路径先做存在性检查；路径不确定时先定位真实路径再搜。
- 加分：区分“路径不存在”（os error 2）与“文件被占用/锁定”（os error 32/33），前者是路径问题不是权限问题。
- 加分：检查相对/绝对路径、大小写与引号转义是否写错。
- 扣分：说“文件被占用/权限不足”——错误归因。
- 扣分：不核对路径就盲目换搜索工具。

## case-10
- 必中：动手前先确认文件实际行数，再设定 offset（176 > 128 已越界）。
- 必中：报错已给出 128 行，应把 offset 调整到合法范围或改读文件末尾附近。
- 必中：改进做法＝偏移读取前先统计行数/探测文件长度，不凭假设或旧行号。
- 加分：直接利用报错中的“128 lines”作为修正依据；分页读取时以实际长度封顶。
- 扣分：说“文件损坏/被截断”。
- 扣分：不核实行数就换更大的 offset 重试。
