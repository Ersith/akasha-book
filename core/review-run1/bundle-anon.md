# 盲评判卷（判卷者用）

说明：每案给出**两份解答**（编号 1/2，顺序随机）。请按 `JUDGE.md` 的四档标准**分别打分**，并给出理由。
你**不知道**哪份来自哪一臂（这正是盲评的意义）；不要尝试猜测来源，只按质量与 rubric 对齐度评分。

## case-01

### 解答 1
1. 本可避免。错因是 `edit` 的 `old_string` 与文件当前内容不完全一致（缩进/空白/换行差异、全半角、BOM/编码，或该处已被更早的编辑改过、或凭记忆与摘要写 old_string）。动手前应：先 `read` 目标区间或 `grep` 定位行号，逐字确认原文，再把"刚读到的原文"整段作为 `old_string`；一次只改一处。
2. 若无法避免：文件在两次读取之间被其它操作改动、或手头只有旧版本上下文时，任何写死的 `old_string` 都可能失配——这属于工具与环境之间的账，单靠谨慎不能把概率降到零。
3. 改做法：固化"**改前先读 — 一次一处 — 改后立即复核**"三步；批量/并行 edit 时逐个文件核对最终内容（"已更新 N 个文件"的计数不算证据）；大范围替换先 `grep` 列出全部命中点再逐点改。自检问句：「我这次 edit 的 `old_string`，是不是我刚读到的原文？」读不到就不改。（库里已有可执行条目 `canon-trap-edit-context-mismatch`：本机 10-06~10-10 共 21 次同类，占全部任务失败约 43%，是最大失败类。）

### 解答 2
1. 可以避免。`edit` 是纯字面匹配替换，报「old_string was not found」说明我给出的锚点不是该文件**当前**的原文——多半是凭印象/凭旧版本复述的（也可能是缩进、换行、引号、编码不一致）。动手前应：先用 `read` 读目标文件（至少覆盖要改的那一段），或先用 `grep` 把候选锚点定位一次，确认它「存在且唯一」，再**原样复制**那段文字去做替换；若该文件可能有别的写入方（脚本、生成器、另一个会话），改前重读一次。
2. 残余不可避的部分很小：只要「锚点取自刚读到的原文」这条被遵守，这类失败基本可以消除；唯有「读取与编辑之间文件被外部并发改写」才仍会落空。
3. 改法三步：① 锚点必须来自刚读到的原文，禁止凭记忆写 `old_string`；② 锚点尽量短而唯一，要改大段就拆成多次小改；③ 收到 not found 时**不重试同一字符串**，先重读文件核对原文，再基于新原文重新构造锚点。

## case-02

### 解答 1
1. 本可避免。错因是把宿主检视面（provider）的**方法名凭印象编写**（`describeService` 不是该 provider 的真实方法）。动手前应：先用 `cordis_inspect_list` 列出 provider 及其**只读方法清单**，再按清单里的确切名字调用 `cordis_inspect_query`；找不到就去查官方文档或源码导出，绝不猜名字。
2. 若无法避免：宿主 API 面会随版本与 provider 清单漂移，且模型侧对非公开方法名没有先验；在没有"先列举"这一步时，首次猜错几乎不可避免。
3. 改做法：把"**先列举、后调用**"作为访问任何宿主 API 的固定前置；猜错一次后**换路径**（去列清单/查源码）而不是换拼写继续猜。自检问句：「这个方法名是我列出来的，还是我想出来的？」（库内条目 `canon-trap-provider-method-list` 在案。）

### 解答 2
1. 可以避免。该查询工具只接受 provider 清单里**声明过**的方法名，`describeService` 是按命名习惯猜的。动手前应先调 `cordis_inspect_list` 取回 provider/method 的真实清单，从结果里挑出确切的 platform / provider / method（必要时读该方法的 input schema），再照抄调用。
2. 基本可避免：报错已表明 provider 名是对的、方法名不存在——属于「先枚举、后调用」就能挡下的错误，而非环境问题。
3. 改法：凡是带「枚举清单」类只读入口的能力面（inspect provider、MCP 工具表、插件服务表），一律**先列后调**，禁止凭名字推断 API；把「名字必须来自清单原文」设为调用前置检查；遇到同类报错就回清单核对、带正确名字重调，而不是连着试几个名字。

## case-03

### 解答 1
1. 本可避免。错因不是正则写错，而是**扫描范围选错**：路径包含被其它进程独占锁定的活数据文件（vectordb store 的 `000119.log` / `MANIFEST-000106` / `LOCK`，os error 32/33），以及 `node_modules` 这类海量生成目录，导致 rg exit 2 整体失败。动手前应：先用 `glob` 列出目标文件，再对**明确文件或浅目录**逐个 `grep`；显式排除 `node_modules` / `.git` / `data` / 正在被服务占用的库目录；路径含空格或中文时加引号。
2. 若无法避免：被其它进程以独占方式打开的文件，任何搜索工具都读不了（Windows 强锁），且"哪些目录正被占用"在动手前未必可知——这类路径注定零覆盖。
3. 改做法：给 `grep` 定两条硬规矩——**只对明确路径执行、只对适合遍历的目录执行**；遇到权限/占用类失败**换副本或降范围，不反复重试同一路径**；换范围前先用 `glob` 探路。自检问句：「这个路径适合 grep 吗？」（库内条目 `canon-trap-grep-exit2-path`，本机四例。）

### 解答 2
1. 可以避免（至少能大幅收窄）。失败是 `rg` 遍历时撞上被独占的文件——正在运行的服务数据目录（`.log`、`LOCK`，os error 32/33）与依赖树，这些本来就不该纳入内容检索。动手前应把 `path` 收窄到源码/文档目录并排除依赖与数据目录（当前 `grep` 工具只支持单个 `include` glob、不支持取反，所以正确做法是**缩小 path**、而不是指望排除语法），只搜目标后缀。
2. 一小部分不可完全避免：被独占文件是**运行时状态**（服务正在写），别的时间点窄范围搜索仍可能碰到；但把它排除在检索范围外即可消除，不是必须承受的失败。
3. 改法：① 默认只搜源码树，绝不从工作区根目录全量搜；② 明确避开依赖目录、数据目录、日志、锁文件、二进制；③ 遇 exit 2 先判「部分失败 vs 全失败」——`rg` 出错时命中仍可能已输出，把报错路径排除后重跑一次拿结果，继续干活。

## case-05

### 解答 1
1. 可以避免。`offset` 是「从第几行开始」，必须小于文件行数；报错已给出真值（22 行）。我拿了一个**没有对当前版本核过**的行号去翻页。动手前应：先不带 `offset` 读一次拿到文件长度与内容锚点（或用一次极廉价的长度探针），再决定是否翻页；或者用 `grep` 定位目标小节，按命中行号开一个带余量的窗口读。
2. 基本可完整避免：行数是可以廉价取得的量，失败根源是硬编码/缓存行号，而不是信息缺失。
3. 改法：① `offset` 只在「同一版本文件、长度已知」时使用，不跨会话、不跨编辑复用；② 想读某段内容，优先 `grep` 定位行号 → 读小窗口，而不是从大偏移盲翻；③ 遇到 out of range 就把行号归一到文件内（或直接从头读），按「锚点过期」处理，别怀疑文件坏了。

### 解答 2
1. 本可避免。错因是 `offset` 不是刚拿到的真实行号——目标文件只有 22 行，却投喂了 30，属"凭印象/沿用旧行号"的跳读。动手前应：先用 `grep` 锚定目标内容拿到真实行号再 `read`；或先 `read` 文件开头确认总行数与规模。
2. 若不可避免：行号会随文件改动整体漂移，且文件可能尚未建立行数缓存；在不知道总行数时，任何"跳读很深的 offset"都可能越界。
3. 改做法：定纪律——**offset 必须来自本回合刚获得的真实行号**；报"越界"后**不再继续猜**，改用 `grep` 锚点重新定位；大文件一律"先 grep 定位、再定点读"。自检问句：「我这个 offset 是刚拿到的行号吗？」（库内条目 `canon-trap-read-offset-range`，本机 10-07/10-08 两例。）

## case-06

### 解答 1
1. 本可避免。错因是参数值超出该工具自述的契约范围——`dsh_wsl` 的 `timeout` 被拒绝（必须 1–300 秒），属"没先读参数范围就投喂边界外值"。动手前应：先查该工具的参数契约（描述/用法），或首次探跑取范围内保守值（如 60），确认链路通再按需调大；报错文案本身已给出合法区间，照它修正即可。
2. 若无法避免：任何"我顺手给了个大 timeout"的操作，在参数契约之外必然被校验拒绝；若事先没看参数范围，首次越界难以完全避免。
3. 改做法：把工具参数契约当**可查项**（工具说明/文档/库内条目）；对"范围型参数"统一取范围内值；同一参数被拒后**不再原样重试**，按报错给出的区间改写；把这类边界型坑写进库，让下次调用前就能看到。自检问句：「我这个参数值在该工具自述的范围内吗？」

### 解答 2
1. 可以避免。这是参数范围校验失败：`dsh_wsl` 的 `timeout` 只接受 1–300 秒，我传了区间外的值（0、负数或大于 300）。工具描述里写着该区间与默认值（60）。动手前看一眼参数约束、把值夹进合法区间即可。
2. 完全可避免，属纯参数错误，没有环境因素。
3. 改法：① 用带硬区间的参数前先看 schema/描述，不用「想快点结束」的 0，也不用「怕超时」的超大值；② 真正需要长时间运行的活，拆成多段（命令内分段、检查点续跑）或走支持后台的通道，而不是把 timeout 往大里写；③ 收到越界报错就按提示夹回区间**立即重发**，不在同一错误上停留。

## case-07

### 解答 1
1. 在**当次调用**层面不可避免：报错主体是子进程运行器本身（`subprocess-local`）——「在证明其受管资源范围已清空之前退出」，退出码 `4294967295` 即 `0xFFFFFFFF`（-1），是被强杀/异常终止的形态；说明失败发生在运行器启动或清场阶段，命令内容根本没执行，换命令、换参数、换工作目录都不会改变结果。若把「本可避免」放宽到源头层面：这类 runner 故障通常有前置诱因（对宿主运行环境或其启动路径做过全局性改动，例如清理宿主环境变量、动运行器目录），那一层是可避免的——但案例材料里没有这个前提，我不替它补。
2. 原因即上：这是宿主级（基础设施）失败，不是任务级错误；工具层没有参数或用法能绕开，重试会同样命中。
3. 改法：① 先用一条无副作用的最小探针命令复现一次，判定是稳定坏掉还是瞬时抖动；② 稳定坏掉 → **停止重试**（这类 runner 故障在进程内一般不自愈），转而排查本会话对宿主环境/启动路径的改动并回滚，再重起宿主进程继续；③ 立规：任何改宿主机环境（环境变量、运行器目录、进程树）的动作，先评估「会不会连坐杀掉子进程通道」，改完立刻用最小探针验证通道还活着。

### 解答 2
1. 本可避免（属环境侧预防）。错因是宿主运行环境卫生被破坏后，Windows Job runner 无法证明自己管理的进程范围已清空，以退出码 `4294967295`（即 -1）终止——这是进程/环境层的故障，不是命令内容错误。动手前应：**不碰宿主进程全局的环境变量**（尤其不要"清理" `ELECTRON_RUN_AS_NODE` 之类的宿主运行模式变量）；不从运行中的进程树里做全局环境清理。
2. 若不可避免：一旦该变量已被删改，或 runner 所在进程树被中断/残留无法回收，**同一进程内无法自愈**，重试多少次都会以同一退出码失败——只能重启桌面端恢复。
3. 改做法：① 把该报错当**环境指纹**归档（退出码 + `subprocess-local` + "before proving its managed range empty" 三件套），下次见到直接走"查近期是否有全局环境变量改动 → 重启桌面端"的分诊路径，不再反复调用同一工具浪费轮次；② 禁止任何"从宿主环境清理 Electron 模式变量"的全局做法；③ 若必须改，只收窄到**应用启动路径**的代码处，而不是动宿主环境。

## case-08

## case-09

### 解答 1
1. 本可避免。错因是**扫描范围过大且未排除生成目录**：对 `profiles\desktop\node_modules` 这类目录（含 junction/链接、且可能在安装/清理过程中被替换）做递归检索，路径不复存在即 os error 2，整次搜索 exit 2。动手前应：用 `glob` 先列出文件确认路径形态，再对明确文件或浅层目录逐个 `grep`；`node_modules` / 数据目录一律显式排除；不从工作区根或 profile 目录整体递归。
2. 若无法避免：安装/卸载/清理会实时改变 `node_modules` 的内容（本机已有"pnpm 顺着链接目录删空依赖"的前例），"此刻不存在"只有探到才知；对这类**频繁变动 + 可能断链**的目录，扫描天然不稳定。

### 解答 2
